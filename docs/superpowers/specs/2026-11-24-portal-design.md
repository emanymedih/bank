# Автобанк-портал — дизайн

Дата: 2026-11-24. Статус: черновик на утверждение. Ветка: `feature/portal-foundation`.
Основание: брейнсторм с владельцем продукта + исследование CRM и РФ-лидеров (`avtobank-crm-ux-research.md` в рабочей папке сессии).

## Зачем

Перекупы в РФ ведут учёт разрозненно: Excel/Google-таблицы, ТГ-чаты. Нет единого места, где машина, деньги, партнёры и договорённости связаны между собой, а изменения имеют автора. Портал централизует это.

Первые 5 минут нового пользователя: регистрация по номеру телефона РФ → создание книги и начального банка → ввод ГРЗ → данные о машине подтягиваются → пользователь дополняет карточку. Дальше — работа с телефона у машины.

## Что решил пользователь (зафиксировано)

- Аудитория: **любые перекупы**, публичная регистрация (не только приглашённые партнёры своей команды).
- Первый сценарий: **ввод номера ГРЗ**, автозаполнение данных о машине, затем внесение остальной информации.
- Перекупы формируют **начальный банк**; все члены книги видят всю бухгалтерию, траты и действия.
- **Таск-трекер по машине — общий** на книгу, не персональный под каждого человека (персональный — излишне).
- **Ссылка на Авито** в профиле машины: видно, по какой ссылке она продаётся.
- **Логин и пароль, привязанные к номеру телефона**, выдаются пользователю.
- **Видно, кто внёс изменения в общий банк и какие они были.**
- «Делай то, что берём» — принят список паттернов из исследования (лента событий, аудит, подтверждение ввода, плотность, роли, итоги этапов, «гараж»-флоу, сессии в ЛК, настраиваемые уведомления).

## Цели

1. Публичный вход по телефону РФ: SMS-подтверждение номера при регистрации, затем вход по логину (номер) и паролю. Восстановление пароля через SMS. Второй фактор не из SMS (TOTP) — следующим шагом (тренд РФ: Госуслуги отключают SMS-2FA из-за перехвата).
2. Личный кабинет: профиль (имя, телефон), безопасность (активные сессии/устройства, выход со всех), мои книги и роль в каждой, приглашения.
3. Общая книга: роли владелец / редактор / наблюдатель; начальный банк; вся бухгалтерия видна членам; приглашение партнёров по номеру.
4. Аудит: неизменяемый журнал «кто, когда, что, было/стало» на каждое изменение книги; лента в карточке авто + журнал книги с фильтрами; внутриприложенческие уведомления о затронутых изменениях.
5. Машина: ввод ГРЗ в стиле номерного знака с автозаполнением (существующий провайдер avtovincod) и понятным fallback (ручной ввод / VIN / фото номера); ссылка на объявление (Авито и др.) в профиле; общий таск-трекер по машине; единая лента событий авто.
6. UX-пакет: предпросмотр «что изменится» перед сохранением быстрого ввода; итоги «вложено» в шапках этапов; закреплённые фильтры реестра на мобильном; единообразие дат/сумм, компактный режим.

## Не-цели и анти-цели

- Не универсальная CRM: без лидов, телефонии, контакт-центра, мессенджеров, email-маркетинга, digital-воронок, мультиворонок автодилера, deal score, геймификации.
- Без drag-and-drop смены этапов: статус выводится из данных и считается «на дату».
- Без конструктора кастомных полей: домен узкий, деньги валидируются сервером.
- Без персональных таск-трекеров (решение пользователя).
- Без нативных приложений на этом этапе (веб/PWA).
- Анти-цель: сломать денежные инварианты — целые копейки, базисные пункты долей, расчёты «на дату», сумма разбивки = итог, защита старых вкладок (409).

## Ограничения

- **152-ФЗ/242-ФЗ**: персональные данные граждан РФ (телефон) должны храниться в БД на территории РФ → хостинг в РФ.
- Текущий стек: vinext (Vite) + workerd/wrangler, D1 (SQLite) + R2; вход сейчас — заголовки среды размещения (`oai-authenticated-user-id`); поиск по ГРЗ — `api.avtovincod.ru/gos2vin` (Bearer-токен, платный, статусы not_found/balance/unavailable уже обработаны).
- AGENTS.md: отдельная ветка; падающий тест до фикса; `npm run check` + `npm run build` перед объединением; независимое ревью диффа для денег/хранения/доступа (скилл avtobank-review-pilot).
- Совместимость: новые поля книги → подъём `ledgerClientVersion` + точечные проверки потери данных старыми клиентами (409).
- SMS: стоимость и доставка, rate limit по номеру и IP (не по cookie), короткий TTL, ограничение попыток, согласие на обработку ПДн.

## Подходы к сборке фундамента

**A. Эволюция на Cloudflare (D1/R2) + своя авторизация.**
Минимум изменений кода, готовый деплой. Но персональные данные РФ-пользователей оказываются в иностранном облаке — риск 152-ФЗ для публичного РФ-портала; доступность из РФ не гарантирована. Отклонён для публичного портала.

**B. Эволюция приложения + деплой на РФ VPS (выбран).**
Тот же код и тесты; на сервере в РФ — workerd (wrangler local-режим с постоянной локальной D1/SQLite и R2/файлами), nginx + TLS, менеджер процесса, бэкапы. Данные не покидают РФ. Минус: wrangler local как production-раннер нестандартен — закрывается конфигом workerd, мониторингом и бэкапами; при росте — миграция на выделенный SQLite-адаптер без смены доменной логики.

**C. Переписывание на классический Node/Next + SQLite.**
Обычный production-стек, но выбрасывает рабочую сборку vinext и переписывает plumbing; долго и против «строить на том, что есть». Отклонён.

Выбор: **B**. Владелец сказал «делай» — выбор сделан мной; если нужен Cloudflare вопреки 152-ФЗ, это вариант A с явным принятием риска.

## Архитектура (фаза 1, эскиз)

Новые таблицы D1:
- `users`: id, phone (unique, E.164 РФ), password_hash, name, created_at, totp_secret (nullable, позже).
- `sessions`: id, user_id, device/ua, created_at, expires_at; cookie HttpOnly+Secure+SameSite=Lax.
- `books`: id, title, owner_id; `memberships`: book_id, user_id, role (owner/editor/viewer).
- `invites`: book_id, phone, role, token, expires_at.
- `otp_challenges`: phone, code_hash, expires_at, attempts (rate limit).
- `audit_events`: append-only; book_id, user_id, at, entity (car/expense/cash/partner/payout/part/task), entity_id, action (create/update/delete), field, before, after.

Книга: текущая таблица `ledgers` переезжает с ключа пользователя на ключ книги; revision и clientVersion сохраняются. PUT книги: серверный diff предыдущей и новой версии → запись аудита с автором; проверки 409/422 сохраняются.

Маршруты авторизации: register (phone → SMS-код), verify-code, login (phone+password), logout, sessions (list/revoke), password-reset (SMS). Провайдер SMS — абстракция `sendCode(phone, code)`; конкретный шлюз и тариф — на строителе (SMSAero/SMS.ru-класс); в dev-режиме код логируется/фиксирован для локальных тестов. CSRF: проверка sec-fetch-site на мутациях (паттерн уже есть в plate-lookup).

ЛК `/account`: профиль, безопасность/сессии, мои книги, приглашения; вход — в правом верхнем углу (привычный паттерн).

Онбординг после регистрации: создать книгу → начальный остаток (cashEntries) → партнёры → первая машина по ГРЗ.

Машина:
- `listingUrl` (optional, https, валидация домена не жёсткая — Авито/Авто.ру/Дром/иное); кнопка «Объявление» в профиле; clientVersion +1 и точечный 409.
- `tasks` по машине: [{id, title, due?, done, author, createdAt}] — общие на книгу; ближайшая открытая задача feeding существующую очередь «Следующие шаги» (совместимость с полем nextAction: миграция или вывод).
- Лента событий авто = работы + расходы + этапы + запчасти + выплаты + аудит-правки, сгруппировано по дню, технические события свёрнуты.

## Фазы (порядок)

1. **Фундамент**: аккаунты, телефонная авторизация, ЛК, книги/роли/приглашения, онбординг, РФ-деплой.
2. **Аудит и лента**: серверный diff, журнал книги и карточки, фильтры, уведомления.
3. **UX-пакет**: общий таск-трекер, ссылка объявления, подтверждение ввода, итоги этапов, закреплённые фильтры, единая лента.

Каждая фаза: ветка, падающие тесты до фикса, `npm run check` + `npm run build`, ревью диффа по AGENTS.md; деньги/хранение/доступ — независимое ревью (avtobank-review-pilot).

## Что остаётся строителю

- Конкретный SMS-шлюз и тариф; хеширование пароля (scrypt из node:crypto без новых зависимостей — предпочтительно); TTL сессий и OTP.
- Production-конфиг workerd на VPS, бэкапы D1/R2, мониторинг.
- Точный формат diff аудита и пагинация ленты.
- Миграция nextAction → tasks без потери существующих записей.
- TOTP — отдельной итерацией после фазы 1 (в фазу 1 не входит).

## Решения, принятые мной (строителем)

- **Партнёр ↔ аккаунт.** `ledger.partners` остаётся записью книги `{id, name}`; у участника книги (membership) появляется необязательная связь `partnerId`. Молчаливый партнёр без аккаунта допустим (перекуп ведёт учёт сам). Приглашение в книгу НЕ создаёт партнёра автоматически: владелец связывает участника с существующей записью партнёра или создаёт новую. «Моя доля» = запись партнёра, связанная с моим аккаунтом. Связь хранится вне денежных данных книги (в memberships), поэтому подъём clientVersion из-за неё не нужен.
- **Удаление и 152-ФЗ.** Самообслуживаемое удаление аккаунта в фазу 1 не входит. Аудит не хранит телефон и имя как ПДн: только user_id + снимок отображаемого имени на момент события; при запросе на удаление строка пользователя анонимизируется, аудит остаётся неизменяемым и обезличенным. Юридическая часть (тексты согласий, уведомление РКН, ответы субъектам) — на владельце вне кода; фиксирую как пробел.
- **Тесты и старая авторизация.** Продакшен-маршруты переходят на сессии; тестовый рантайм (`tests/support/api-runtime.mjs`) адаптируется под новую авторизацию так, чтобы все существующие проверки остались зелёными. Судьба старого деплоя и живых книг — вопрос к владельцу (ниже).
- **Уведомления** в фазе 2 — внутриприложенческие (бейдж + лента); пуш/почта — позже, с настройкой типов и объяснением ценности при запросе доступа.

## Ответы владельца (24.11)

1. **Живых книг нет — чистый лист.** Миграция и claim-флоу не строятся. Таблица `ledgers` сразу ключуется по книге; фото сразу ключуются `cars/{bookId}/{photoId}`. Заголовочная авторизация ChatGPT выпиливается из продакшен-маршрутов; тестовый рантайм адаптируется под сессии так, чтобы существующие проверки остались зелёными.
2. **Инфраструктуры пока нет — решим позже.** Фаза 1 заканчивается проверяемым локальным сервером (workerd/wrangler local с постоянной локальной D1/R2), конфигами деплоя, бэкапами и инструкцией РФ-развёртывания. Публичный запуск, аренда VPS/домена и договор со SMS-шлюзом — отдельное решение владельца перед стартом; до него SMS работает в dev-режиме (код логируется/фиксирован для локальных тестов), провайдер — абстракция `sendCode`.

## Критерии успеха

- Новый пользователь: регистрация по телефону → книга → машина по ГРЗ быстрее 5 минут (приёмочный прогон на локальном сервере; на живом — после решения об инфраструктуре).
- Любое изменение общей книги имеет автора и «было/стало», находится за два клика.
- Партнёр без бухгалтера видит свою долю и ситуацию по машине.
- Все существующие 76 тестов зелёные + новые тесты авторизации/ролей/аудита/совместимости; `npm run check` и `npm run build` проходят.
